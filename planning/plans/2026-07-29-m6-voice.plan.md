## Verified before planning

Probed rather than assumed, the same way M3's flags were:

- **Voicebox answers on `127.0.0.1:17600`.** `/health` returns 200. The
  `17493` in Voicebox's own README is stale — it is the container-internal
  port. This closes the discrepancy flagged back at M0.
- **Endpoints that matter:** `GET /health`, `GET /profiles`,
  `POST /generate {profile_id, text}`, `GET /audio/{generation_id}`,
  `POST /transcribe {file}`.
- **Five voices exist** — Bella, Nicole, Adam, Michael, Emma.
- **`model_loaded: false` at rest.** The first generation has to load a model,
  so the first speech is slow and the UI must not read that as a hang.
- GPU is available (RTX 3060, CUDA).

## Process

### Requirements

1. Voicebox status visible, with start/stop.
2. Down → text-only, said plainly. The app keeps working.
3. Push-to-talk in, `assistant.speak` out, **subtitles always**.
4. MUTE, and a speaker button on every assistant message.

### Design decisions

- **All Voicebox HTTP goes through Rust.** Not a preference — the webview
  *cannot* do it. WebKitGTK serves the app from an opaque origin, so a
  cross-origin response is discarded no matter what `Access-Control-Allow-Origin`
  says. Professor proved this by experiment, including confirming the server
  returned a matching allow-header and the webview rejected it anyway. Adding an
  HTTP client to the Rust core is therefore forced, and it talks to
  **localhost only**.
- **`/generate` + `/audio/{id}`, not `/speak`.** `/speak` plays server-side;
  fetching the audio and playing it in the app is what makes MUTE, the speaker
  button, and M7's amplitude-driven mouth possible at all.
- **Never touch `/cloud/*` or `/llm/generate`.** Voicebox has cloud features
  that may bill. Everything used here is local inference on hardware already
  bought. No paid path is reachable from GIT HUD.
- **Speech is opt-in per message, plus automatic for `assistant.speak`.** D15:
  the agent speaks summaries; code and diffs are for reading, and the separate
  event type is what makes that structural rather than a promise.
- **Subtitles always.** Nothing is only spoken (`ui-layout.md`).
- **A slow first generation is not a failure.** The model loads on first use;
  the UI says "loading the voice model" rather than appearing hung.

### Phases

1. `voice/` in Rust — health, profiles, generate, fetch audio, transcribe.
2. Supervision: status polling, a `voice://` status the panel can show.
3. UI: status pill, MUTE, speaker button per assistant message.
4. Push-to-talk: capture in the webview, bytes to Rust, Rust posts to
   `/transcribe`, text lands in the composer.
5. Validation.

### Risks

- **Microphone permission in WebKitGTK.** `getUserMedia` may need a Tauri
  permission and may simply be unavailable; if so, push-to-talk degrades to a
  stated limitation rather than a silent dead button.
- **First-generation latency** being read as a hang.
- **Audio format** from `/audio/{id}` needing a container the webview will play.
